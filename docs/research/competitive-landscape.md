# Signalpost: product research and release standard

Research date: **18 October 2026**. Repository baseline: `0d6cd48`.

The intended product serves **campaign teams, developers monitoring transactional email, and sales teams**. The credible common product is a trustworthy email activity workspace: create or connect a message, identify its intended recipient, see what happened, and understand what the evidence actually proves. Each audience needs a different workflow around that common core.

A polished interface can improve adoption. An acquisition by Google or any other company cannot be promised or inferred from appearance. Commercial readiness also requires proven demand, repeat usage, reliable operations, sound unit economics, and a product that owns a useful problem.

## Research method and limitations

This report combines direct repository inspection with read-only inspection of five vendors' official public GitHub repositories through the available Git proxy. Source references below pin the inspected commits. They establish documented API capabilities, **not** usability, vendor reliability, feature availability on a particular plan, or customer satisfaction.

Direct HTTPS requests to the official Resend, Postmark, Loops, Customer.io, Brevo, Linear, Google support, Apple support, and W3C pages returned proxy CONNECT **403**. Consequently, this is an evidence-based initial competitive assessment, not a completed hands-on market study. Current prices, plan limits, authenticated competitor screens, performance benchmarks, and independently verified customer outcomes are deliberately omitted. Loops, Mailchimp, Mailsuite, and Linear remain follow-up research candidates; their current capabilities or visual details have not been verified here. No interviews or customer tests have been conducted.

## Differentiation to test

**Proposed positioning:** “One clear email activity record for your team.” The hypothesis is that small teams will value a shared, understandable view across campaign and operational email without overstated engagement metrics.

The shared core should expose workspace, recipient, message, channel/workflow, external message ID, timestamp, event source, and confidence/limitations. Campaign teams enter through audience and content. Developers enter through an integration and message ID. Sales users enter through a contact and connected inbox. Keep one visual system and common activity vocabulary, but release the specialized integrations in stages.

Validate the hypothesis with at least five target users per audience. Observe each person completing a real task, record time-to-first-value, misunderstanding of delivery/open states, and whether they return with a second real use case. Do not use praise of screenshots as evidence of retention or willingness to pay.

## Product and visual acceptance criteria

The following are proposed release gates, **not results already achieved**.

| Dimension               | Acceptance gate                                                                                                                                                                                                                    | Evidence to collect                                                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core tracking           | A new selected-recipient campaign produces unique, concrete recipient tokens; captured HTML contains no unresolved placeholders; a public pixel request appears on that recipient and never another workspace.                     | Local capture SMTP plus two recipients, unique links, actual HTTP requests, database/API assertions, and independent account verification.                |
| Bulk honesty            | Shared HTML is labeled campaign-level tracking. Adding a contact or copying HTML without merging its token never implies named attribution.                                                                                        | Walk through both external-send and direct-send paths; inspect recipient and campaign counters.                                                           |
| Privacy/bots            | Raw events and estimated unique activity have explicit definitions. Blocked images and proxy traffic do not imply an unread/read fact. Bot/proxy flags show their heuristic basis.                                                 | Human-readable tooltips and tests of known proxy/scanner user agents, repeat requests, and absent images.                                                 |
| Delivery semantics      | Queued, processing, SMTP accepted, provider-confirmed delivered, bounced, and failed are distinct. An unavailable provider signal shows unavailable rather than zero or a fabricated success.                                      | Worker lifecycle tests, provider fixture tests when integration exists, and UI review against real records.                                               |
| Metric definitions      | Counts specify unique recipients versus total events. Rate labels state the denominator; missing denominator is shown as unavailable. Comparisons use equal ranges and consistent timezone boundaries.                             | Hand-calculated fixtures including empty data, repeat opens, clicks without opens, bulk events, and bot activity.                                         |
| Navigation and layout   | Every destination works by keyboard and touch; active location is visible; icon-only navigation has accessible names and discoverable labels. Mobile navigation closes appropriately and restores focus.                           | Browser tests at 360, 390, 768, 1280, and 1440 CSS pixels; keyboard walkthrough; no page-level horizontal overflow at narrow widths or 200% zoom.         |
| Visual consistency      | One spacing/type/color system; stable alignment, table density, control heights, and page headings. Reuse the requested purple navigation rail while prioritizing readable content.                                                | Reviewed reference screenshots for overview, campaign list/detail, recipients, analytics, settings, and mobile navigation. Record intentional exceptions. |
| Accessibility           | Target WCAG 2.2 AA: contrast 4.5:1 for ordinary text, 3:1 where applicable for large text/UI, visible keyboard focus, programmatic labels, reduced-motion support, and meaningful errors.                                          | Automated audit plus manual keyboard, zoom, screen-reader, and contrast checks. Automated audits alone do not establish conformance.                      |
| Every page state        | Loading, empty, filtered-empty, permission-denied, partial failure, and retry paths explain the next action. No fake metrics, decorative controls that promise unavailable functionality, or misleading success toasts.            | Role-based walkthroughs with empty and populated fixtures, failed requests, slow network, and expired sessions.                                           |
| Performance             | Initial target: Core Web Vitals “good” thresholds—LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at the 75th percentile; keep interactions responsive on representative low-power mobile hardware.                                                | Local traces are diagnostic only; establish real-user monitoring before claiming field performance.                                                       |
| Security and operations | No cross-workspace access; server checks all mutations; tracking tokens resist guessing; secrets stay server-side; untrusted HTML cannot execute in the app. Auth recovery, backup restore, and migration rollback have a runbook. | Negative authorization tests, dependency audit, HTML/URL tests, staging migration rehearsal, restore exercise, and alert verification.                    |
| Commercial readiness    | A pilot cohort repeatedly completes real workflows; support and monitoring ownership are defined; running costs per active workspace are measured.                                                                                 | Cohort retention and paid-pilot feedback. Set retention/pricing targets after discovery rather than inventing market proof.                               |

“Pixel perfect” should mean an agreed visual system implemented consistently across realistic content, devices, and states. A single desktop screenshot does not establish product quality.

## Phased rollout for all three audiences

1. **Repair and establish trust.** Reproduce the reported open-attribution failure using locally captured email. Fix token generation/personalization and route durability as the evidence requires. Make sending mode, tracking origin, unresolved merge fields, and public reachability visible before sending. Add regression coverage. Preserve production data; investigate live configuration separately.
2. **Polish the common workspace and campaign workflow.** Apply consistent navigation, cards, tables, filters, content hierarchy, and mobile behavior. Prioritize overview → recipients → campaign → send readiness → recipient activity. Define all metrics and surface queue/error state. Validate with campaign users.
3. **Add a developer workflow on the same event core.** Introduce scoped/revocable API keys, a documented transactional-message ingestion/send contract, external message identifiers, one provider adapter with verified webhooks, deduplication, replay behavior, delivery status, and diagnostics. Ship a tested minimal SDK/example only after the API contract stabilizes.
4. **Add a sales workflow on the same contact timeline.** Choose Gmail or Microsoft integration based on actual pilot demand. Add scoped OAuth, connection/revocation status, per-message instrumentation, reply/conversation association, and contact ownership. Extend to CRM and follow-ups only after inbox behavior and consent/suppression rules are verified. Do not imply an extension already exists.
5. **Prove the business and operational standard.** Run paid pilots across the three cohorts, improve the strongest retained workflow, confirm sustainable sending/support costs, rehearse migration/restore, and independently assess security and accessibility. Set availability and support targets with staffing and monitoring to support them. Broader distribution or acquisition discussions follow evidence of value.

The phases are ordered by dependency and risk, not promised calendar dates. Specialized transactional and inbox integrations must not displace the immediate tracking bug or make current campaign use harder.
