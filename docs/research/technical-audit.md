# Signalpost technical and product readiness audit

Audit date: 18 October 2026. Baseline: commit `0d6cd48`. This is a read-only review of the checked-out source before the accompanying implementation work. References below describe that baseline; subsequent fixes must be verified independently.

## Conclusion

Signalpost has useful foundations for an owner-operated email tracking product: database-backed workspace membership, server-side role checks, recipient tokens, a persistent delivery queue, suppression checks, and signed billing webhooks. It is not yet ready to market as a fully managed, multi-tenant email delivery service. The most urgent work is reliable recipient attribution, safe campaign state transitions, durable audience admission, and honest reporting of image-proxy activity.

No P0 issue (demonstrated unauthenticated account compromise or cross-tenant data disclosure) was established by this review. Several confirmed P1 defects block a dependable paid launch. This conclusion is not a penetration-test certification or a statement about the deployed Supabase/Vercel configuration: no production database queries, external mail sends, payment requests, or deployment changes were performed.

An attractive interface can improve adoption, but acquisition by Google cannot be guaranteed or established by pixel accuracy. A defensible target is a reliable product for a specific customer group, with clear analytics definitions, independently tested tenant boundaries, evidence of retention, documented operations, and maintainable code.

Billing regression command: `node scripts/test-billing.mjs`. It exercises 121 local checks against the actual TypeScript handlers with mocked Prisma/Stripe and blocks network access inside the process. It covers every plan/status combination, quota accounting at UTC boundaries, signature/body rejection, retry/rollback, duplicate handling, authoritative subscription snapshots, obsolete identities, and checkout idempotency. It does not charge a card, send mail, or connect to any database. Queue admission has a separate local regression script, `scripts/test-queue-admission.mjs`; the final release must additionally run the application integration suite against a dedicated local database.

Billing configuration now requires both `STRIPE_WEBHOOK_SECRET` (event authentication) and `STRIPE_SECRET_KEY` (current subscription lookup), with the configured plan price IDs. A Stripe lookup failure returns a retryable webhook failure without consuming the event ID or opening a database transaction. No real provider credentials were used by these checks.

## Severity definitions

- **P0:** immediate stop; demonstrated critical compromise or uncontrolled data loss.
- **P1:** resolve before paid/general availability, or constrain the affected capability explicitly.
- **P2:** improve before scale; usability, consistency, or a conditional architectural risk.

## P1 findings

### T1. Test emails can either lose attribution or contaminate campaign metrics

**Confirmed by source tracing.** `src/app/api/campaigns/[id]/send-test/route.ts:54` creates a random `testToken` but does not persist it. Lines 65–69 substitute this token into already-generated selected-recipient HTML. The open handler resolves only a persisted `CampaignRecipient.trackingToken` (`src/app/api/track/open/[token]/route.ts:33`), so these opens silently produce no event. Conversely, raw HTML is instrumented in bulk mode at send-test lines 56–61, creating a shared live campaign token. Such test opens enter the campaign's real event totals.

**Acceptance:** a captured test email contains resolvable, persisted tracking identity tied to the intended test address; opening and clicking it are attributable in the test view; test events are explicitly excluded from production campaign metrics and engagement segments. Test both raw HTML and already-instrumented HTML. Do not infer a person's identity from IP addresses.

### T2. Previously tracked HTML bypasses instrumentation validation

**Confirmed by source tracing.** Send admission uses `htmlContent.includes("/api/track/")` to decide whether processing is necessary (`src/app/api/campaigns/[id]/send-blast/route.ts:164`). The same shortcut appears in send-test at line 56. One stale pixel, a foreign campaign's link, or even matching incidental content can skip processing of otherwise untracked HTML. The worker replaces placeholders and the current campaign's bulk token only (`src/lib/mailer.ts:303`), leaving unrelated tokens unchanged.

**Acceptance:** processing is idempotent and validates campaign ownership of each tracking link/pixel. Raw, partially tracked, stale-host, and other-campaign HTML all result in exactly one correct pixel and correct link attribution. Reprocessing must not create nested redirect chains.

### T3. HTML generation can reopen an active or completed campaign

**Confirmed by source tracing.** `src/app/api/campaigns/[id]/generate-html/route.ts:43` unconditionally writes `status: "READY"`. It does not guard the existing status. Send admission trusts `DRAFT`/`READY` (`src/app/api/campaigns/[id]/send-blast/route.ts:189`); deletion only protects `ACTIVE` campaigns (`src/app/api/campaigns/[id]/route.ts:23`). Generating HTML can therefore release the send lock while work is pending, allow deletion during delivery, or permit another admission to replace subject/content. The worker reads campaign content during each delivery (`src/lib/mailer.ts:279`), so different queued recipients can receive different content.

**Acceptance:** generation cannot change an active/completed campaign's state. Sending uses an immutable content/audience version. Concurrent generation, send admission, and deletion preserve the state machine. Reusing a sent design requires an explicit duplicate/new campaign operation.

### T4. Queue admission is only partially durable

**Confirmed architectural failure window; not fault-injected against a database.** The campaign is marked active before `blastCampaignToAudience` runs (`src/app/api/campaigns/[id]/send-blast/route.ts:189`, `:209`). That function inserts recipients/deliveries one by one (`src/lib/mailer.ts:136`, `:175`, `:185`) without an atomic campaign admission record or expected audience manifest. Request termination can leave only part of the intended audience queued. Subsequent normal send admission rejects the active campaign. Recipient-level enqueue errors are summarized as exclusions rather than providing an explicit resumable admission state.

**Acceptance:** interrupted admission is resumable with a stable idempotency key, immutable target audience, expected/queued/skipped counts, and a clear admission state. A fault injected mid-admission must neither lose intended recipients nor duplicate delivery records. Worker claims and SMTP acceptance must remain distinct from admission completion.

### T5. Closing the sending page can leave a campaign waiting days

**Confirmed configuration and documented limitation.** `vercel.json:5` runs the worker once daily. `src/app/api/cron/deliveries/route.ts:81` processes at most 100 items per run. The main paced delivery loop lives in the browser (`src/components/campaigns/HtmlGenerator.tsx:209`). Closing the page therefore turns a time-sensitive send into a daily batch queue. A 500-message backlog requires at least five daily runs without further browser processing, before retries or competing workspaces are considered. A larger workspace can also monopolize global FIFO processing.

**Acceptance:** server-owned scheduling and an appropriately frequent, authenticated worker progress the queue without a browser. Define a dispatch latency target, per-workspace fairness and send-rate limits; measure them in staging. Until then label this an operator-driven/internal tool and show the daily fallback delay before sending. Do not silently promise near-real-time delivery on the checked-in Hobby schedule.

### T6. Paid entitlements are granted without checking usable billing state

**Confirmed by source tracing.** The webhook stores a paid plan even when checkout is unpaid/`INCOMPLETE` (`src/app/api/billing/webhook/route.ts:88`) or a subscription is incomplete (`:122`). Recipient imports read only `plan` (`src/app/api/recipients/route.ts:60`) and send admission does the same (`src/app/api/campaigns/[id]/send-blast/route.ts:137`). Consequently a workspace with a paid plan but incomplete payment receives the paid quota. The retry worker also has no entitlement check.

**Acceptance:** a central entitlement policy defines active/trial/grace/canceled/incomplete behavior and is used consistently by admission, imports, workers, and billing display. Test incomplete payment, failed initial invoice, delinquency, recovery, cancellation, and downgrade while deliveries remain queued. If charging is not part of the initial release, hide/disable checkout until this policy is verified.

### T7. Billing lifecycle is vulnerable to races and out-of-order events

**Confirmed missing safeguards; consequence established by source ordering.** The webhook correctly verifies signatures and atomically deduplicates event IDs (`src/app/api/billing/webhook/route.ts:19`, `:190`). However it stores no event ordering/version or authoritative reconciliation state (`prisma/schema.prisma:90`). Subscription updates overwrite workspace entitlement based on metadata/customer (`webhook:122`), while invoice events update by customer alone (`:153`). A delayed update can overwrite a more recent cancellation or subscription replacement. Checkout performs a read, calls Stripe, and returns without a local pending checkout lock or idempotency key (`src/app/api/billing/checkout/route.ts:28`, `:68`), allowing simultaneous subscription sessions before any webhook links the first one.

**Acceptance:** event delivery in reverse order produces the same final entitlement as delivery in order; events for an obsolete subscription cannot reactivate a replacement/canceled account. Repeated/concurrent checkout cannot create duplicate billable subscriptions. Reconcile with Stripe's authoritative current subscription when ordering is ambiguous. Test duplicate events as well as different IDs referring to the same lifecycle change.

### T8. Workspace limits are non-atomic and usage definitions disagree

**Confirmed by source tracing.** Monthly admission is a separate count followed by enqueue (`src/app/api/campaigns/[id]/send-blast/route.ts:146`, `:209`). Concurrent campaigns can each pass the same available quota. Recipient admission has the same count-then-upsert race (`src/app/api/recipients/route.ts:77`, `:117`). Admission counts non-canceled deliveries by **queued month**; billing displays only sent/delivered records by **sent month** (`src/app/(dashboard)/billing/page.tsx:27`). Failed/queued sends can consume invisible quota, and a previous-month backlog sent this month escapes the admission month's count.

**Acceptance:** quota reservation and admission are atomic per workspace with concurrent requests. Publish one definition for reserved, consumed, released, failed, test, and month-boundary usage; show the same ledger in billing and admission. Tests include simultaneous campaigns/imports and a queue spanning UTC month rollover.

## P2 findings and product gaps

### T9. Image proxies and humans are conflated; segmentation disagrees with reporting

**Confirmed by a local, dependency-free function check and source tracing.** `src/lib/errors.ts:18` labels every `GoogleImageProxy` request automated. The legacy Apple-style user agent is explicitly treated as non-automated at line 14. Neither pattern proves that an actual person opened an email. The analytics unique-recipient queries exclude automated events (`src/app/(dashboard)/analytics/page.tsx:262`), but segments use any matching event without this filter (`src/lib/segments.ts:42`). A recipient with only a scanner click can therefore be in a "clicked" segment even when unique-click reporting excludes them.

Local check on Node 24.19.0: importing `isAutomatedUserAgent` and testing representative strings returned `true` for Gmail's image proxy and `false` for the explicitly exempt Apple browser string. No network or database was used.

**Acceptance:** preserve raw events while separating observed image loads, image proxy/privacy loads, suspected automated scanners, and unknown/human-likely activity. Display confidence/limitations. Use a single, versioned classification policy for metrics, recipient activity, and segments. A Gmail proxy image request should not automatically imply a scanner click or a confirmed human read.

### T10. Recipient activity only lists deliveries created by this app

**Confirmed by source tracing.** `src/app/api/campaigns/[id]/analytics/recipients/route.ts:35` starts from `CampaignDelivery`, whereas exported manual merge tokens create only `CampaignRecipient` records (`src/app/api/campaigns/[id]/export-admin-csv/route.ts:61`). A correctly tokenized external send can have identified open/click events yet be absent from recipient activity. Shared bulk HTML can never identify which audience member loaded it; adding an audience contact alone does not personalize copied HTML.

**Acceptance:** clearly separate internal-delivery, external recipient-merge, and aggregate-only workflows. Show attributable external events without inventing delivery status. Warn before exporting shared bulk HTML. Historical shared-token opens cannot be assigned to named recipients after the fact.

### T11. Onboarding cannot recover from an expired verification link

**Confirmed missing flow.** Signup creates a unique email account and a 24-hour verification token (`src/app/api/signup/route.ts:60`, `:83`). Expired verification returns 410 (`src/app/api/signup/verify/[token]/route.ts:27`). Retrying signup returns account exists (`signup:94`). No resend-verification route or self-service forgotten-password flow is present in the API tree. A solo owner must depend on privileged operator recovery.

**Acceptance:** rate-limited verification resend and account recovery use hashed, single-use, expiring tokens; generic responses avoid unnecessary email disclosure. A verification token cannot reactivate memberships disabled later by an administrator. Test expired, used, superseded, and concurrently redeemed links.

### T12. Account-wide password reset needs a stricter boundary before multi-workspace support

**Conditional architectural concern, not a demonstrated cross-tenant exploit through current onboarding.** A workspace admin can reset a target member's global password (`src/app/api/admin/users/route.ts:101`). If a user belongs to another workspace, that action grants control of the shared account and affects its sessions everywhere. The schema allows multiple memberships, though current invite creation rejects an existing email (`src/app/api/admin/invite/route.ts:75`) and login always picks the first active workspace (`src/lib/auth.ts:53`).

**Acceptance:** workspace administrators manage membership only. Account password recovery requires the account holder's proof or an explicitly trusted platform-operator process. Before allowing existing users to join another workspace, implement workspace selection and adversarial two-tenant membership tests. Do not sell multi-workspace account support until this is resolved.

### T13. Deliverability and consent history are incomplete for a managed sending product

**Confirmed product boundary.** SMTP success is recorded as `SENT`, not inbox delivery (`src/lib/mailer.ts:327`). Although the schema includes delivery/bounce/complaint timestamps, no provider feedback endpoints populate them. Sending identity is a server-wide SMTP configuration (`src/lib/mailer.ts:16`), with no per-tenant verified sending domain flow. Re-importing an opted-in contact overwrites consent timestamps (`src/app/api/recipients/route.ts:130`), and repeated unsubscribe POSTs overwrite unsubscribe time (`src/app/api/unsubscribe/[token]/route.ts:45`), so current timestamps are not an immutable subscription history.

**Acceptance:** keep "SMTP accepted" distinct from confirmed delivery; ingest authenticated provider bounce/complaint feedback and suppress appropriately before a managed-email launch. Define sender ownership/domain authentication. Store append-only consent changes for auditable trends. An internal tracker can defer a sending platform, provided its product copy and supported workflow state this boundary plainly.

## Positive controls observed

- Protected API handlers use active database-backed workspace membership and role checks; campaign/recipient lookups reviewed are scoped by workspace. Membership and password changes invalidate sessions (`src/lib/auth.ts:92`). No unauthenticated workspace data access was found in the inspected paths.
- Last-admin protection uses a serializable transaction (`src/app/api/admin/users/route.ts:43`) and blocks self-demotion/disable.
- Invitation tokens are random, stored hashed, expire, and are claimed atomically (`src/app/api/invite/accept/route.ts:27`). Verification claims are transactional too.
- The queue persists delivery state, uses conditional claims to avoid simultaneous normal processing, and rechecks suppression (`src/lib/mailer.ts:249`). SMTP timeout uncertainty and potential duplicate retries are documented rather than promising exactly-once delivery.
- Public click redirects validate HTTP(S), and recipient tokens from another campaign cannot be assigned to a click (`src/app/api/track/click/[token]/route.ts:23`, `:51`).
- Unsubscribe GET presents a confirmation rather than changing state, and POST applies a workspace suppression transactionally (`src/app/api/unsubscribe/[token]/route.ts:45`).
- CSV export escapes formula-leading values (`src/app/api/campaigns/[id]/export-admin-csv/route.ts:96`).

## Practical release sequence

1. **Reliable tracker pilot:** fix T1–T3; make supported sending/export workflows explicit; prove actual generated email -> open/click -> named recipient end to end. Add mobile/keyboard/accessibility and screenshot checks to the core campaign flow. Keep reports honest about image loading and scanners.
2. **Operational sending beta:** address T4–T5 and shared classification; measure queue progress without a browser; add observability, restore-tested backups, explicit privacy/retention controls, and sender identity checks. Exercise failure, retry, and partial-outage cases in staging.
3. **Paid launch:** resolve T6–T8 and verification/recovery; implement billing and two-tenant adversarial integration suites; settle provider feedback and support/runbook responsibilities. Turn on charging only when the tested entitlement policy matches the published terms.
4. **Scale based on customer evidence:** choose a focused segment such as small operational-email teams, document the workflow they prefer over alternatives, and measure activation, retention, tracking coverage, and support load. Acquisition value requires customer/product evidence beyond a visual redesign.

Suggested release evidence: reproducible integration tests and screenshots at narrow mobile/tablet/desktop widths, verified accessible forms/navigation, exact analytics definitions, signed-webhook replay tests, quota concurrency tests, queue crash tests, a demonstrated database restore, and a deployment checklist with no secret values.

## Review limitations

This document is a source audit, not a statement that every failure was reproduced in the running app. "Confirmed by source tracing" means a deterministic missing guard or conflicting code path is visible; conditional concurrency outcomes and deployment capacity should additionally be reproduced in isolated staging. No production data or credentials were read, no external mail was sent, and no database changes were made by this audit. Repository files may be changing concurrently as fixes are implemented; use the baseline commit for the line references above and verify remediation against the final commit.

## Validated release evidence

The implementation’s local validation passed a production build, TypeScript, lint, 100 tracking end-to-end assertions, 108 application/authentication assertions, 121 mocked billing checks, 34 database-backed queue checks, 13 origin checks, and invitation template escaping checks. Tracking tests capture email locally and route simulated public pixel/click requests to the isolated app. No external email or production database mutation is part of these tests.

Browser evidence includes the actual studio copy/download workflow, persisted per-recipient pixel attribution visible in analytics without a queue delivery, and zero Signalpost tracking requests from a draft preview. Populated, empty, and read-only overview states were checked at 360–1280px; its scoped axe scan found no WCAG 2A/2AA/2.1AA violations. This is automated evidence for those views, not full manual WCAG certification. Fixture screenshots are in `/workspace/scratch/product-review` in the working environment.

Source research and local checks cannot establish production deliverability, hosted Supabase pooler behavior under load, verified customer demand, reliability SLAs, or acquisition value. The open items above remain explicit release gates.
